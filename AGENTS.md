# Cadencia — agent notes

## Build & test

- `CadenciaCore/` is a plain SwiftPM package with no Apple-framework imports. Test it with `swift test` in that directory (Swift 6 toolchain; works on Linux). Keep it that way: anything needing HealthKit, CoreBluetooth, SwiftUI or Speech belongs in the app target.
- The app target (`Cadencia/`, `Cadencia.xcodeproj`) only builds in Xcode 16+ on macOS. If the hand-written pbxproj misbehaves, `xcodegen generate` from `project.yml` recreates it.
- No Xcode in orbs: when editing app sources without a Mac, compile-check what you can by moving logic into `CadenciaCore` and testing it there.
- `web/` is a pnpm workspace (TypeScript, Effect 4, `@alchemy.run/domain` on Cloudflare). From `web/`: `npx pnpm@10 install`, `npx pnpm@10 test`, `npx pnpm@10 typecheck`. See `web/README.md`.
- `web/` pins Alchemy `2.0.0-beta.85`. Its API is older than the alchemy plugin's docs: views take `validate` inline (no `toLayer`), Apis have no `queries`, commands take no `{ description }`. Check the installed sources or the `v2.0.0-beta.85` tag's `examples/cloudflare-domain` before following the plugin.
- Two bounded contexts, `planning` and `coach`, over three shared packages: `identity` (who acts and whose data it is: `AthleteId`, `Actor`, `Session`, `mustOwn`), `kernel` (the Shared Kernel: calendar days, plan ids, text, training terms) and `athlete` (what Intervals says about the athlete: evidence, readiness, measures). They import only `effect`, `@alchemy.run/domain` and the shared packages above them (`kernel` → `identity`; `athlete` → `kernel`); `web/packages/server/test/Boundaries.test.ts` checks it.
- No hand-routed HTTP. Everything the Worker serves over plain HTTP besides the domain's own Apis (the session, signing in, the athlete's Intervals reads) is declared in `@cadencia/web-api` (`WebApi`: `HttpApiGroup`s of `HttpApiEndpoint`s with annotated schemas, typed errors with `httpApiStatus`, the `Authentication` security middleware), implemented with `HttpApiBuilder.group` in `server/src/WebHttp.ts`, and called by the app through `HttpApiClient`. Its OpenAPI is at `/api/openapi.json`. A request that doesn't match its schemas answers 400 (`RequestValidation`). Infrastructure (Cloudflare, HTTP, Intervals, D1) lives in `server`. Coach never imports Planning: it reaches it through the `Planner` external system.
- A type goes in `kernel` only if both contexts use it, it means the same in both, and a change to it must reach both at once. Otherwise it belongs to the one context that uses it (`SessionId` and `ExternalId` to Planning; `MessageId`, `Headline` and `Attempt` to Coach), even if the server or the app also reads it.
- Policies run at least once. A policy that calls the `Planner` passes `requestFor(envelope)` (the triggering event's `stream:seq`); the server sends it as Planning's `commandId`, so a repeated request is applied once and answered the same way.
- A Day is the athlete's local day, which the domain has no time zone for: commands that act "from today" (`RetirePlan`, `ReviseWeek` through `AcceptIntent`) take `today` from the athlete's client, and Planning refuses one more than a day from the UTC date (`ImplausibleToday`). Only policies fall back to the UTC date.
- Every reference a command accepts is checked in its `decide`: a Coach command that names a plan (`planId`) refuses one that isn't the caller's (`NotYours`), and the `Planner` acts as that athlete, so Planning checks it again.
- External systems declare their errors (`Calendar`: `CalendarUnavailable`, `CalendarRefused`); a policy records a refusal as an event (`SessionPublicationFailed`) and leaves an outage to its `retry` and the platform's redelivery. Never `orDie` a vendor's answer in an adapter.
- Every view declares a `version`; bump it when its state or fold changes. An event's shape must keep decoding what is already stored, unless the stage is destroyed and deployed again. Stack state lives in Cloudflare (`Cloudflare.state()` in `web/alchemy.run.ts`).
- Planning and Coach share one Worker. Build every Api over its own model's internals (`overPlanning`/`overCoach` in `web/packages/server/src/Hosting.ts`); otherwise the second model hides the first.
- Specify behaviour with Alchemy stories (`Story.make`) in each domain package; server tests host both models in memory with the real `Planner`.
- iOS talks to the backend through `CadenciaCore/Sources/CadenciaCore/Backend/`: `CadenciaAPI.generated.swift` is generated from `ClientApi`'s OpenAPI (`CadenciaCore/OpenAPI/openapi.json`) by `npx pnpm@10 --filter @cadencia/server ios-client` from `web/`; never edit it by hand. Each domain brand (`PlanId`, `Day`, `Minutes`, `Title`, …) becomes a Swift type that checks the brand's pattern, length or range (`CadenciaAPI.Branded`): `scripts/openapi.ts` recovers brand names and the patterns Effect leaves out of JSON Schema from the domain packages and marks them `x-brand`. Build ids with `BackendID`, AI text with `init(fitting:)` and typed text with `init(text:)`. `CadenciaAPI.swift` (transport, session, errors), `BackendTranslation.swift` (app types ↔ wire) and `CoachBackend.swift` (commands, then waiting for the policy's answer) are hand-written.
- The iOS ↔ backend contract is checked from both sides without a deployment: `BackendContractTests` (Swift) pins the command bodies in `CadenciaCore/Tests/CadenciaCoreTests/Fixtures/backend-requests.json`, and `web/packages/server/test/IosContract.test.ts` replays them through the `/v1` HTTP API and pins the views iOS decodes in `backend-views.json`. After changing either side, regenerate with `CADENCIA_UPDATE_FIXTURES=1` (Swift first, then web).
- `Tests/AppStateTests.swift` runs with `python3 Scripts/test-app-state.py` (no iOS host needed).

## Conventions

- Intervals.icu is the system of record. The iOS app persists a single `AppState` JSON plus one JSON per ride; its plan, conversation, consultation, today's decision and rider profile there are only caches of the backend's views (`CurrentPlan`, `ConversationThread`, `ConsultationView`, `TodayDecision`, `RiderProfileCard`), replaced on every read.
- The web backend (`web/`) stores only what Intervals has no field for: plan intent and phases, conversation, consultations, daily decisions and the AI rider profile, as events in Durable Objects (EU jurisdiction). Intervals OAuth tokens live encrypted in D1, outside the events, so they can be deleted.
- The AI runs only in Cadencia iOS, with the athlete's own ChatGPT plan (Sign in with ChatGPT is documented for local, open-source apps). The backend never calls an LLM: iOS records each interpretation (model, evidence, fingerprint) through `IosCoachApi`, and Planning accepts or refuses it. The web writes only what needs no AI. iOS signs in at `/auth/intervals/start?client=ios` (there is no other way in), keeps the session token in the Keychain and calls the `/v1` API: `RecordDailyDecision` (re-asking the AI with the plan's refusal, at most twice), `SendMessage`/`RecordCoachReply`, the consultation commands and `RecordProfileAttempt`/`RecordProfile`. Plan changes that need no AI (`MoveSession`, `RecordDayRequirement`, `RetirePlan`, `AcceptIntent`, `DismissIntent`) are the same commands the web sends. `/v1` publishes only `IosCoachApi` and `IosPlanningApi`: give each HTTP client its own Api rather than publishing the web's. The backend publishes planned sessions to Intervals (`CalendarPublishing`); iOS never does. `POST /auth/exchange` also hands iOS the athlete's Intervals OAuth token (`intervalsAccessToken`), kept in the Keychain and sent as Bearer for iOS's own Intervals calls (ride uploads, wellness, settings, calendar entries, notes, streams); there is no API key. A lapsed 30-day session only pauses the plan and the coach, and an Intervals 401 only the Intervals calls, until the athlete signs in again from Settings, which replaces both.
- Anything Intervals has a native field for (wellness feel/sleep/motivation/mood/stress/injury/comments, weight, height, units, Ride FTP, weekly availability, goal event, time away, other training, planned rides' indoor/FTP/type) is only cached in `AppState`. Local edits go into `IntervalsOutbox` (or `CalendarSync` for calendar entries) and are read back on refresh; Intervals wins unless a local change is still unsent. A plan's Intervals-native parts (availability, time away, other training, the goal event's priority and course) are kept in `PlanContext` next to the cached plan. Ride evaluations (debriefs) stay with each ride.
- All mutation goes through `AppModel` methods; views read `model.state` and never write it directly. `AppState.plan` changes only by reading the backend's view or Intervals back; a change to the plan is a backend command.
- User-facing strings are English source keys with Spanish in `Cadencia/Resources/Localizable.xcstrings`. Use `LocalizedStringKey` for view text and `String(localized:)` for strings handed to non-view APIs.
- Uploads must stay idempotent: every ride has an `externalID`, and an `.uncertain` ledger entry is reconciled by that id before any re-upload.
- Readiness can soften a day's prescription, never harden it beyond the plan. This rule, and every other check of a session against the plan, lives only in Planning (`web/packages/planning/src/Plan/PrescriptionRules.ts`); iOS only range-checks the AI's JSON (`DailyPrescription.parse`).
